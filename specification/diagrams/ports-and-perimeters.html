Ports & perimeters

Every connection sruti has is opened from the Mac, outward — the managed Mac's endpoint filtering destroys anything inbound, and the design never needs it. Four perimeters sit between an operator's key and the four sections on screen: the air, the receiver's site, the internet, and the Mac itself, with the app's window inside it.

The perimeters, outside in

The air · HF

Operators key CW in the 7 and 14 MHz band segments; the NCDXF beacons on 14.100 MHz are the known-answer test signal. sruti can only ever be on the receiving side of this boundary: there is no path back.

The receiver's site · ws :8073

A public KiwiSDR someone else owns. Decoding happens here, in its CW_decoder extension — text, not audio, is what sruti consumes in v1 (audio decoding on the Mac is v2). sruti is a guest: one slot, a clear name, polite backoff.

The internet · :443, :8073

Crossed only by connections the Mac opens: the receiver WebSocket, the Gemini API call for each piece, the Claude API call (button-gated), and the receiver directory. Nothing out there can initiate a connection in.

The managed Mac · inbound ✕

The hard perimeter. Endpoint filtering destroys every inbound LAN or internet connection, so sruti is built to need none. Secrets stay inside: .env holds the two API keys, gitignored and never printed; sessions live in var/sessions/.

The window · no port

A native macOS window from pywebview on the system WebKit. The page is handed over as a string and talks to the core only through the JS bridge, so nothing in sruti listens on any port — not even loopback.

In process · events

Inside sruti the core (receiver link → segmenter → store → explainers) talks to the interface only through the event stream and the core commands. The window is a shell over the core, which never imports interface code.
